Development workflow

Idea to Code

As of 2026-11-24, a toy trial ran the flow from explore to verify, end to end. No real change has gone through the flow yet.

The idea becomes an OpenSpec change, built in thin slices, one at a time; where a repo has specs, the tests are written from the spec first, and the code may not change them.

Built on OpenSpec and on skills adapted from Matt Pocock's AI Hero skills.

In a repo with OpenSpec, feature work is always delivered as a change: never as a plan alone, and never as direct code.

What the flow assumes

  • git
  • pull requests that squash-merge
  • OpenSpec 2.x in each repo
  • a coding agent with skills and fresh sub-agents
  • a test command in each repo
On a line
  • where it starts
  • a check, a ruling or a question

Build

Build: each slice becomes tests, then code

the build command14 stops for the owner

The owner types the build command, or asks for the build in words and the session loads it. Then the agent works alone.

Who is who

  • The session: writes no test and no code.
  • The test writer: tests at the Seam; expected values from the spec, never from running code.
  • The code writer: code until the tests pass.

The code writer never

  • edits, adds, deletes or renames a test file or fixture
  • special-cases a test input as the fix

What happens

In the example

    1. The change folder

      No change named, and several changes active: which change to build.

  2. Before the first slice

    1. Sets up once

      • from the repo root
      • git status
      • the default branch
      • the working branch
      • the apply guidance

      Optional Many repos, owner gates

      branchrefuse-empty-file-name

    2. The set-up questions go to the owner

      • the default branch, when none of main, master or the remote's default exists
      • an unrelated change in the tree
      • whether the first commit carries a term or decision record from explore
      • a clash with the apply guidance
      • a command the config does not name

      The OpenSpec config names the test command, after Tests:.

      No question: the first tests commit carries the change folder.

  3. Per slice

    1. (a)gate passes(b)test_empty_file_name_is_refused(c)FAILED: expected 400, got 201 right reason(d)tests commit 1, Tests-For: S1(e)check in upload/handler.py(f)no changed test file(g)pytest passes; code commit 2

    2. The gate stops the build

    3. The red check

      Before any code for the slice exists, every new test must fail for the right reason. Without check scripts, the session runs it by hand, as slice-build describes.

      Optional Check scripts: scripts run the slice check, the gate, the red check and the test-lock check.

    4. The trailers of a tests commit stop the build

      • the trailer block fails its check, or git cannot write it
      • a resumed build cannot tell from the Tests-For trailers which slice resumes

    5. A writer hands back an owner decision

      The session asks the owner.

  4. When something goes wrong

    1. A part fails: fresh writers retry Default

      slice-build holds the exact rule.

    2. The last retry fails: the build stops

      One question to the owner, with the evidence.

    3. If the code writer says a committed test is wrong: the spec rules, never the code writer

      Default The steps are defaults; that the spec rules is the owner's decision.

      Optional A repo without specs

    4. The code writer finds a bug: where it sits decides Default

      • A test reaches it, or the code is newFixed in the slice.
      • No test reaches it, in this change's codeA fix slice, built next.
      • Older than the changeA lead in the final report.

        Goes to the owner as a scope question only when the slice cannot be done without the fix.

    5. Every slice closed on the working branch; nothing pushed

      The owner gets the final report. The session writes it to build-report.md and commits that file alone.

      The check command fails at that commit: correct the report, or stop.

      slices with commitsfour commitsassumptionsonebugs, disputed tests, failed checksnone

In the example

      code review (the message is inline)one breachsmell: Primitive Obsessiona leadunasked worknone

      comparisonnone

    6. No finding: verify has passed

      Optional Owner gates

    7. If verify has findings: one fix round, then verify once more

      One question each: a tests commit of an earlier fix round at the end of the working branch; each test-lock offence that no answer in build-report.md covers (keep the edit, or restore the test); each finding about a past commit that no answer covers (keep the commit, or fix it in a new commit); every bug on a Bugs left line; a finding still open after the second verify; every stop of a failure default; a failed check command at the commit of build-report.md; every hand-back of an owner decision.

      • no bug becomes a fix slice
      • inside a change, refactoring only as a Fix finding that cites a written standard

      Default A listed lead does not keep verify from passing.

Who does what: the owner decides, the agent does the work

Who is who

  • owner The owner: answers every question; approves what the flow leaves to the owner.
  • The session: the agent conversation the owner talks to; makes every commit.
  • A sub-agent: fresh, one job; commits nothing, ticks no task box, starts no other agent.

The agent looks up every fact, and checks it at its source or by running it. A code comment is not a source. It never asks the owner for a fact it can look up.

Five kinds of owner decision

  1. scope
  2. a public contract
  3. a breaking change
  4. a security trade-off
  5. a new dependency

How the agent asks: one question per message, one form

Heading

### Error text, Q1 of about 3: What does the refusal tell the uploader?

Background: Today the service stores a file with an empty name and answers 201. The change will refuse it. The uploader must see what was wrong.

Options:

A. Name the field (recommended)

- A 400 error whose message names the field: filename must not be empty.

- Pro: the uploader sees at once which field to fix.

- Con: one more message in the messages file.

B. A plain refusal

- A 400 error with the generic text bad request.

- Pro: no new message.

- Con: the uploader must guess what was wrong.

Recommendation: A. The service's other errors name their field (the error form in the upload handler).

Last line

Next: answer A or B.

A small change: two shortcuts

Small: one repo, at most two task sections Default

The fast path: skip step 1

Propose first checks four things, read-only:

  • the outcome and the done-test each fit in one sentence
  • no owner decision is open
  • at most two task sections
  • no assumption is open

One fails: step 2 writes nothing and points to the explore command.

No Slices section

Each task section is one slice, built in order.

Default

  • each slice depends on the section before it

The agreed seam stands on a Seam: line under each task heading.

A bug: where it is found decides its road

  • During a buildstep 3
  • In the fix roundstep 4
  • Reportedthe diagnosing-bugs loop, below

    1. Redacts every secret first

    2. Builds a loop that goes red on the bug

    3. Minimises the repro

    4. Ranks its hypotheses and shows them to the owner

      Without waiting when the owner is away.

    5. Tags its debug logs

    6. Writes a regression test where a correct seam exists, then the fix

    7. Checks the cleanup

It writes loop code: never inside a read-only step such as explore.

When no loop can be built: one question, three options.

  • access to an environment that reproduces it
  • a captured artifact, secrets redacted
  • temporary instrumentation in production, named as a security trade-off

No loop, no hypothesis.

Redacted output not enough: one question for the missing signal.

An enhancement store: major features, designed before any repo change

When
major features that span repos; the size of the feature decides
Without it
the track question loses its first two questions

    1. A live entry: one OpenSpec change in the store

    2. The accept step

      It refuses the entry while an open question is blocking or answered.

    3. Repo changes deliver its task lines; each names the entry line

    4. A pull request on the store ticks the line

    5. A delivered entry is archived

A store correction carries no new behaviour, and cites only merged changes.

The flow names no entry command: each project makes and changes entries its own way, and its profile says how.

Open Whether size alone makes work an enhancement; the store checks no delivered line. until then step 1's track question stands; the profile says how the project checks one.

A tracker issue: one change per repo, one issue ties them

When
work over several repos that is not a major feature; without a store, all work over several repos
Without it
each repo's change stands alone; nothing checks that every repo was done

The issue body

an intro sentence
[ ] repo, PR link   (in merge order)
Not affected: repo, reason
Store correction (where there is a store)

    1. Explore lists the open tracker issues first

    2. The owner approves the repo list; no approval, no issue

    3. A link when a pull request opens

      Each pull request body ends with a Part of <issue URL> line.

    4. A tick when it merges

    5. One close

      By the session that merges the last pull request, once every line is ticked.

Release rules: the title's type may decide who merges

When
a release tool versions from the titles of squash-merged pull requests
Without it
one merge rule for every pull request
  • Cuts a release, for example feat fix waits for the owner's approval
  • Cuts no release, for example chore testwhere the merge rule says so, the agent merges under the merge conditions

The owner can override. Default An override works either way, one pull request at a time.

A repo without specs: no tests first

When
a repo's OpenSpec schema has no specs artifact
Without it
every repo has a specs artifact, or such repos stay outside the flow

    1. No delta specs; a Done when line covers each user story

    2. A bug in this change's code: fixed in the slice's commit Default

    3. The check command; no red check, no test-lock check

    4. The archive only moves the folder

Default A disputed test, or a needed test change, goes straight to the owner.

Open A small change here has no Done when line. until then the profile says how the project builds one.

Owner gates: the agent decides whether the owner looks

When
the owner wants to see the plan or the verified change, only where a look matters
Without it
no owner gate runs; the owner still decides at every stop
  • soft: no hook, no script
  • both on; Plan gate: off. or Result gate: off. turns one off
  • the owner can override for one change

The plan gate: after propose

Default The owner looks when:

  • the plan rests on an assumption
  • a public contract, or a breaking change

The result gate: after a passed verify

Default The owner looks when:

  • verify needed a fix round
  • the final report names a disputed test, a bug or a stop
  • a lead or an Owner finding is still in the report
  • No criterion holdsThe gate passes; the work goes on.
  • One holds The owner reviews the real files in the review tool, or answers one question.
    • approve
    • approve with changes
    • change and show again

The agent never approves for the owner. While the owner is away, the work waits.
