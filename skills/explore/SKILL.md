---
description: "Explore an idea in the current repo before any change is written. Use it to start work on an idea, a topic or an existing change, in place of the repo's openspec-explore skill."
argument-hint: "[idea]"
---

Run the explore step of the Idea to Code flow in the current repo.

Idea: $ARGUMENTS

The text after `Idea:` is the idea in the owner's words. It may also be a topic, or the name of an existing change to think about. When the line holds no text after the colon, take the idea from the owner's message that started this command. When that message holds none, ask the owner for the idea in one plain sentence, and wait for the answer.

Explore is read-only. Write no code and no change folder, and do not run `openspec new change`. The propose step writes the change, so decline every offer of OpenSpec's explore skill to write change files. Explore makes two writes: the move forward of the fresh-base check in step 1, and the ledger of step 5.

1. From the repo root, run the lines of Default branch and of Fresh base, in the `CHECKS.md` of the `idea-to-code:slice-build` skill, in one shell call. Read that file for these two sections only, and start no build. Act on the result as Fresh base says. Then read the repo guide (`AGENTS.md`, else `CLAUDE.md`), the files it names and `openspec/config.yaml`.
2. Load the repo's `openspec-explore` skill with the Skill tool, and give it the idea. Its name stays bare, because the repo holds this skill and the plugin does not. When the session does not list it, read `.agents/skills/openspec-explore/SKILL.md`, else `.claude/skills/openspec-explore/SKILL.md`, and follow that text. When neither file exists, say so and stop. Do not run the step from memory.
3. Look up the facts before you ask anything: the code, the tests, the docs, the active changes, and each spec under `openspec/specs/` that the idea touches. A spec that the idea does not name can still state the behaviour it changes: search every spec under `openspec/specs/` for the key terms of that behaviour (the field, the function, the old value or wording), and read each hit. Read those specs also for rules on how the work is done: a requirement with `never`, `only`, `must`, `always` or `no`. An option of the grill that breaks such a rule changes the spec, and its background says so. When the idea comes from an issue, a report or another person's text, list the claims it makes: the cause, the proposed fix, and the result that the fix should give. Check each claim in the code before the first question, and do not take a proposed fix as true because the issue proposes it. Trace what the fix would do with the errors, values or inputs that occur in practice. Where a claim rests on what a library or a tool does at run time, settle it with the `idea-to-code:prototype` skill. Start your first answer with a `Checked claims:` list: each claim, then true, false or open, then its source (a file and line, or the prototype). A claim that stays open and that the design rests on is an assumption: the grill asks it, or a side step settles it.
4. When the idea asks how to make something possible, it is a design question. Present the researched design, your recommendation, the open questions and one proposed next step. Then stop. Before the owner approves the design, write no change folder, no entry in an enhancement store, no branch and no pull request. When the owner approves the design, go on with step 5, unless the answer names another next step. The grill then asks each open question, one per message.
5. Load the `idea-to-code:grilling` skill and run the grill. Where OpenSpec's explore skill and the grill differ, the grill wins. Every question has the grill's form, and the questions go on until the grill's stop rule ends them. Name a ledger to the grill, `openspec/explore/<name>/questions.yaml`, where `<name>` is a short name of the idea in kebab-case. Read the `LEDGER.md` of that skill, and write every question and every choice of your own there as it says: the entry first, with its predictions, then the question. Among the questions that the frontier allows, ask in the order of the scopes: product, then architecture, then program design. Ask a point of program design (the file or package that holds a part, a type and its fields, a function signature, the call path) only when it has two real options and no written rule settles it: the repo guide, a decision record, the glossary or a spec. Otherwise decide it yourself, and write it to the ledger as a choice. Ask the seams among those questions. A seam is a point of program design. A seam is the public interface where tests go, and every seam is agreed with the owner before the change is written. Ask the seams after the decisions that fix what is built, because a seam depends on them. Ask one question per distinct seam, not one per slice. Start the name in its heading with `Test seam`. Say in its background that the build writes the tests there before the code, and then locks them. Name the parts of the work whose tests go there. Each option keeps the form of the grill: its example line, then `Catches:` as its pro and `Misses:` as its con, in place of `Pro:` and `Con:`. The recommended option shows its `Misses:` line too. The grill says when to pause for the `idea-to-code:prototype`, `idea-to-code:research` and `idea-to-code:domain-modeling` skills.
6. When a reported bug needs a diagnosis loop, name the bug and pause explore. Load the `idea-to-code:diagnosing-bugs` skill, and resume explore with its finding. That skill writes loop code, so it runs apart from explore.
7. Ask a track question only when the repo guide names an enhancement store or tracker issues, and ask it as the guide says. Otherwise the work is one change in this repo, and no track question is asked.
8. Write the record, from the ledger. List each decision with its mark: the owner's answer, your assumption, or delegated. List each agreed seam as a decision, with the parts of the work whose tests go there. Name the ledger and its path. List each file that a skill wrote and that is not committed, the ledger included. List each scratch folder of a side step, with its full path.
9. Name the next step: `/idea-to-code:propose`, as the last line of your answer, after the record (the Next line is the last line, as the form of the grill wants everywhere). It runs in this session: the ledger holds the decisions, and the facts that explore looked up live only in this conversation. When the owner asks you to capture the talk as a change, write no change file in explore: that request is for the propose step, and the propose command writes the change. When explore ends with no change, commit an uncommitted file only when the owner asks.
