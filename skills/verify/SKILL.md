---
description: "Verify a built OpenSpec change in the current repo. Use it whenever the user asks to verify a change, in place of the repo's openspec-verify-change skill. It runs the repo's test command, check command and test lock, applies the repo's openspec/verify.md where that file exists, runs OpenSpec's comparison, fixes the findings in one fix round, and ends with the owner gate for the result."
argument-hint: "[change-name]"
---

Run the verify step of the Idea to Code flow in the current repo.

Change: $ARGUMENTS

Select the change first. When the `Change:` line holds a name after the colon, use it. When it holds no text, use the change that this conversation names. With none named, run `openspec list --json` and use the only active change. With several active changes, ask the owner which one, as one question in the form of the `idea-to-code:grilling` skill. With no active change, say so and stop: there is nothing to verify. Say which change you use. Run the steps below in order: a step starts only when the step before it is done.

1. Work from the repo root. Read the repo guide (`AGENTS.md`, else `CLAUDE.md`), the files it names and `openspec/config.yaml`.
2. Read the state of the change: `openspec instructions apply --change <name> --json`. Verify takes in a change whose every slice is closed. When the state is blocked, show what is missing and stop. When a task is not complete (`progress.remaining` is above 0), the build has not ended. Report each task section that holds an open box, name `/idea-to-code:build <name>`, which resumes the build, and stop.
3. Test whether the verify rules file exists: `openspec/verify.md`, from the repo root. Do this on every run, with a command or a file read. Do not answer it from memory or from a line of the config. OpenSpec's own verify skill does not name this file, so this command does. Test also that the repo's `openspec-verify-change` skill is there: the session lists it, or `.agents/skills/openspec-verify-change/SKILL.md` exists, or `.claude/skills/openspec-verify-change/SKILL.md` exists. When it is not there, say so and stop. Run no check first.
4. Run the checks of the repo, in the order below, from the repo root. A failure is a finding. When the config does not name a command that this step needs (the test command in a repo with specs, the check command in a repo without specs), first ask the owner one question in the form of the `idea-to-code:grilling` skill, with the command that you find in the repo's build files as the recommended option. The command of the owner's answer holds for this run and for its fix round. An answer that names the check command also holds for each commit: give it to the `idea-to-code:commit` skill.
   - The test command (the command after `Tests:` in the `context:` of `openspec/config.yaml`), once. A repo without specs (its schema has no `specs` artifact) runs only the check command, which is its test command.
   - The check command (the command after `Checks before a commit:` in the `context:` of `openspec/config.yaml`), once. A repo with specs and no `Checks before a commit:` line has no check command: say so in the report.
   - The slice check script (the command after `Slice check:` in the `context:` of `openspec/config.yaml`), where the config names it. Run it as its `--help` says.
   - In a repo with specs, the test lock. Load the `idea-to-code:slice-build` skill for this check only, and start no build. Run the commands of Test lock at verify in its `CHECKS.md`, with or without check scripts. Never run the test check script (the command after `Test check:` in the `context:` of `openspec/config.yaml`) at verify: it compares the tests with one slice's tests commit. A repo without specs has no tests commit, so it has no test lock. That block reads the owner's answers on earlier offences from `build-report.md`: an `ANSWERED` line is no finding, and an `OFFENCE` line or an `UNCOMMITTED` line is one. Ask no question on an offence at this step: the fix round asks it.
5. Apply the verify rules, before OpenSpec's comparison.
   - The file exists: read all of it. Apply every rule in it in this run, and do every check that it names. Load a skill that it names by the full name. For the code review that is `idea-to-code:code-review`, because the short name loads another skill. Each breach and each failed check is a finding that cites its rule. Add no code review of your own: the file says whether one runs.
   - The file does not exist: load the `idea-to-code:code-review` skill once. Then read the diff that the code review read: from the merge-base with the branch that the work merges into, to `HEAD`. A requirement, a scenario, a task or a Done when line must ask for each behaviour that the diff adds. Each miss is a finding.
6. Run OpenSpec's comparison. Load the repo's `openspec-verify-change` skill with the Skill tool, for the same change. Its name stays bare, because the repo holds this skill and the plugin does not. When the session lists it, load it with the Skill tool, and never read its `SKILL.md` with `cat` or a file read in its place. Only when the session does not list it, read `.agents/skills/openspec-verify-change/SKILL.md`, else `.claude/skills/openspec-verify-change/SKILL.md`, and follow that text. Steps 4 and 5 already ran the test command, the check command, the slice check script, the test lock and the verify rules. When that skill, the repo guide or the config asks for them again, do not run them a second time in the same pass. Each CRITICAL issue and each WARNING issue of its report is a finding.
7. Write one report. Its first line names the verify rules that ran: `Verify rules: openspec/verify.md`, or `Verify rules: none, by hand`. Then list the findings of steps 4, 5 and 6, each with its source. Then list each answered offence (`ANSWERED` lines) and each `IGNORED RECORD` line of the test lock, so that the owner sees them. Then list the leads. A lead is a smell or a suggestion that cites no written rule. End with the `Project rules:` line of the code review, where one ran. Write this report as text to the owner, in your reply, before step 8: before the fix round and before the result gate. Do it on every pass, the second pass of the fix round too. A tool call or a loaded skill is no report.
8. Give the verdict, only after the report of step 7 is written as text for this pass. With no finding, verify has passed. A lead stays in the report and does not keep verify from passing, unless the repo guide says that a listed lead is an open finding. With findings, load the `idea-to-code:slice-build` skill and run its fix round (After verify). Where the fix round says to run verify once more, run steps 3 to 7 of this command again, once. The second run does every check again on the new diff: it loads the code review and the repo's `openspec-verify-change` skill again, and shows a report of its own. A finding that is still open then goes to the owner, as that skill says, and verify has not passed.
9. After a passed verify, and only after the report of step 7 is written as text for the pass that passed, load the `idea-to-code:owner-gate` skill and apply the result gate. The gate starts after the report, never before it. Push nothing before the gate ends.
10. Report the outcome of verify and of the gate. Then say what follows. This command ends here.
    - Verify has passed, and the result gate has an outcome in `gates.json`: name the archive, with the repo's `openspec-archive-change` skill, and the pull request, with the `idea-to-code:pr` skill.
    - In every other case: say that verify has not passed, or that the result gate waits for the owner. List what is with the owner. Name no archive and no pull request, and push nothing.
