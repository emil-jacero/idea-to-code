## Local skills

- `idea-to-code:commit`: picks the commit type, the scope, and how to split changes into commits. It reads the project's commit, release and text rules from the repo, and uses Conventional Commits where the repo says nothing. It holds five flow rules: the text bans (no session ID, no session link, no "Generated with" footer, no model or version name in an attribution or signature line, no bare `@name`), never amend a commit, put it to the owner when a hook blocks a command, the message of every tests commit ends with the trailer `Tests-For: <slice name>`, and the check command runs before every commit that is not a tests commit. Where the repo names a check command, the skill runs it after its checks of the message and before `git commit`. A failed check command stops the commit, and the report of the skill holds a `Check command:` line. The value `none` is refused on `Tags:`, on `Publishing:` and on `Mentions:`, because the default of each is a ban. The skill then stops, and asks the owner for the rule in words. Before the check command, it stages again only a file that it staged and that changed since. A file that the owner staged keeps the owner's index entry.
- `idea-to-code:slice-build`: builds an OpenSpec change slice by slice: per slice a fresh test writer, then a fresh code writer (only the code writer in a repo whose schema has no specs). A fresh test writer rules on disputed tests from the spec, a bug left in code the change committed becomes a fix slice, and one fix round follows verify. The repo's `openspec/config.yaml` names the test command, the check command, the test-file patterns and, where the repo has them, the two check scripts; the plugin ships no check script. `idea-to-code:commit` runs the check command before every commit that is not a tests commit, and the build runs it no second time. After the last slice, the build writes its report to `build-report.md` in the change folder and commits it alone, and the fix round appends its own report. The build names `/idea-to-code:verify` for a fresh session, and it does not start verify itself. On a request in words to build, the description sends the session to `/idea-to-code:build`, which loads this skill. It takes the place of upstream `skills/engineering/implement`. Some ideas (a reason for each input of a brief, compile-only stubs, red for the right reason, a disputed test reported instead of a workaround, routing each finding to the role that owns it) follow upstream `skills/engineering/tdd`, `skills/engineering/implement` and `skills/engineering/code-review`. No upstream text is copied.
- `idea-to-code:owner-gate`: applies the two owner gates of a change, the plan gate after propose and the result gate after a passed verify. Both gates are on, unless a gate line turns one off: `Plan gate: off.` or `Result gate: off.` The line stands in the repo guide (`AGENTS.md`, else `CLAUDE.md`), or in the `context:` of `openspec/config.yaml`. It decides by written criteria whether the owner reviews the work, runs the review (with a review tool such as Plannotator where one exists), and records the outcome in the change's `gates.json`. It stops with one question to the owner in two cases: a line says in other words that a gate is off, or the build report, `build-report.md` in the change folder, is missing at the result gate and no other criterion of that gate holds. A record with the outcome `skipped` holds `outcome`, `source`, `reason` and `datetime`. The build and the first push check that record. No upstream text is copied.

## Step commands

Each command starts one step of the flow in the current repo.

- `/idea-to-code:explore`: starts explore. It runs the repo's `openspec-explore` skill. It loads `idea-to-code:grilling`, and `idea-to-code:diagnosing-bugs` for a bug that needs a diagnosis loop.
- `/idea-to-code:propose`: starts propose. It runs the repo's `openspec-propose` skill. It loads `idea-to-code:owner-gate` for the plan gate, `idea-to-code:slice-build` for the form of a slice only, and `idea-to-code:prototype` or `idea-to-code:research` for the evidence folder.
- `/idea-to-code:build`: starts the build. It runs no generated skill. It loads `idea-to-code:slice-build`.
- `/idea-to-code:verify`: starts verify. It runs the repo's `openspec-verify-change` skill. It loads `idea-to-code:code-review`, `idea-to-code:slice-build` for the test lock at verify and for the fix round and `idea-to-code:owner-gate` for the result gate.

The four commands were written for this flow. No upstream text is copied.
